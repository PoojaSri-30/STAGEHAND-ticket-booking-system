# System Design Write-Up

## Seat hold & TTL mechanism

Each event has a live seat map in `show_seats` — one row per physical seat
per showing, generated by cloning the venue's reusable `venue_seats`
template at event-creation time. This separation lets one venue host many
events without their seat states colliding.

When a customer selects seats and starts checkout, `POST /bookings/hold`
creates a `seat_holds` row (`event_id`, `customer_id`, the held
`seat_ids`, and `expires_at = now + SEAT_HOLD_TTL_SECONDS`, default 10
minutes) and flips the matching `show_seats` rows to `status = 'held'`.
Held seats are immediately visible to other customers as unavailable via
the seat map endpoint and a WebSocket broadcast.

Expiry is enforced two ways. A backend scheduler (`jobs/scheduler.js`)
ticks every `SCHEDULER_INTERVAL_MS` (default 15s), asking
`seatService.releaseExpiredHolds()` to find every active hold past its
`expires_at`, release its seats back to `available`, and mark the hold
`released` — this is the authoritative, server-side guarantee that no seat
stays locked forever. On top of that, the frontend runs a live countdown
against `expires_at` and reacts immediately if it reaches zero locally, so
the UI never lags behind by a full scheduler interval. Explicit checkout
abandonment (`POST /bookings/hold/:id/release`) and successful confirmation
both close the hold out immediately rather than waiting for either path.

## Concurrency prevention

The core risk is two customers holding or booking the same seat at once.
This is prevented with an atomic conditional UPDATE rather than
application-level locking:

```sql
UPDATE show_seats
SET status = 'held', held_by = ?, hold_id = ?, hold_expires_at = ?, version = version + 1
WHERE id = ? AND event_id = ? AND status = 'available'
```

Whichever concurrent request's UPDATE statement is executed first by the
database flips the row and reports one row changed; any other request's
identical UPDATE affects zero rows, because `status` is no longer
`'available'` by the time it runs. There is no read-then-write gap for a
race to land in — the WHERE clause and the write happen as one atomic
database operation. A `version` counter is incremented on every state
change as a secondary audit trail.

For holds covering multiple seats, every seat's conditional UPDATE runs
inside a single database transaction. If any seat in the batch is already
taken, the transaction throws and rolls back entirely — a customer never
ends up holding a partial, unwanted subset of their selection. This exact
pattern was verified by firing two simultaneous `hold` requests for the
same seat from two different customers: one call succeeds with a holdId,
the other receives a clean `409 Seats unavailable` naming the contested
seat, with no double-hold ever occurring.

The same WHERE-guarded UPDATE approach is what powers waitlist offers and
booking confirmation, so the no-double-booking guarantee holds across the
entire seat lifecycle, not just the initial hold. It also translates
directly to Postgres/MySQL (as `SELECT ... FOR UPDATE` or the same guarded
UPDATE), so moving off SQLite for horizontal scaling doesn't require
redesigning the concurrency model.

## Waitlist auto-assignment flow

Once a seat category sells out, customers can join a per-event,
per-category FIFO queue (`waitlist` table, ordered by a `position`
counter). The trigger for auto-assignment is a booking cancellation:
`POST /bookings/:id/cancel` releases the cancelled seats and immediately
calls `offerFreedSeatsToWaitlist()`, which groups the freed seats by
category and, for each category, offers them to the earliest waiting
customer whose requested quantity fits what's available. The offer uses
the identical guarded-UPDATE hold mechanism, so a freed seat can never be
raced away by a normal customer between cancellation and the waitlist
offer being placed.

## Time-limited offer handling

An offer sets `waitlist.status = 'offered'` and `offer_expires_at = now +
WAITLIST_OFFER_TTL_SECONDS` (default 15 minutes), and emails the customer
a link to a countdown page. Three outcomes are handled:

1. **Accept** (`POST /waitlist/:id/accept`) — the already-held seats are
   converted straight into a confirmed booking with a QR ticket, the same
   code path as a normal checkout confirmation.
2. **Decline** (`POST /waitlist/:id/decline`) — the seats are released and
   `offerFreedSeatsToWaitlist()` is re-run immediately for that category,
   cascading the offer to the next customer in line without delay.
3. **Timeout** — the scheduler's `expireStaleOffers()` runs on the same
   tick as hold expiry, finds any `offered` entry past its
   `offer_expires_at`, releases its seats, marks the entry `expired`, and
   re-runs `offerFreedSeatsToWaitlist()` — so an unresponsive customer
   cascades the seat to the next person automatically, bounded by the
   scheduler interval rather than requiring a customer action to unstick
   the queue.

This gives a strict, self-healing FIFO: seats never sit idle waiting on an
unresponsive customer for longer than one offer TTL plus one scheduler
tick.
